# 后端代码阅读指南（deploy-agent）

> 本文档面向第一次接触本项目的读者，给出"先看什么、后看什么、每一步看什么"的完整路线。
> 阅读顺序的设计原则：**先看小文件建立全局认知，再看大文件深入细节；先理解"Agent 被告知做什么"，再理解"系统怎么让它安全地做"。**

---

## 一、这个项目是做什么的（先建立全局认知）

一句话：**用 AI Agent 自动完成软件部署**。

用户在网页对话里说"帮我部署 xxx 仓库的 xxx 分支"，后端 Agent 会按顺序自动执行：

```
拉取代码(git pull) → 构建镜像(docker build) → 停旧容器 → 删旧容器 → 启新容器 → 健康检查
```

其中"停容器 / 删容器 / 启容器 / 回滚"等危险操作**必须等人工审批**（在对话里点同意/拒绝），这是整个系统最核心的安全设计。

### 技术栈一览（不熟悉的概念见文末"名词解释"）

| 技术 | 在本项目中的作用 |
|---|---|
| FastAPI | Web 框架，对外提供 HTTP 接口 |
| DeepAgents / LangGraph | Agent 框架，负责"LLM ↔ 工具"的循环调度、中断恢复、会话记忆 |
| LangChain | 提供 @tool 装饰器、Message 消息体系等基础能力 |
| ChatOpenAI | 调用 OpenAI 兼容接口的大模型 |
| SSE (Server-Sent Events) | 把 Agent 的执行过程实时推送给前端 |
| paramiko | SSH 客户端，所有 git/docker 命令都通过 SSH 在目标服务器上执行 |
| aiosqlite / SQLite | 三个轻量数据库：对话检查点、部署状态、审计日志 |
| pydantic-settings | 读取 .env 配置文件 |
| loguru | 日志库 |

## 三、推荐阅读顺序（八个阶段）

### 阶段 0：项目外围（看配置，理解"系统运行需要什么"）

| 顺序 | 文件 | 看什么 |
|---|---|---|
| 1 | `.env.example` | 每个配置项的注释。重点理解三组：LLM 配置、目标服务器 SSH 配置、**三类白名单**（容器名/镜像前缀/workspace） |
| 2 | `pyproject.toml` | 依赖列表，对照上面的技术栈表 |
| 3 | `skills/deployment/SKILL.md` | **必读**。这是 Agent 的"操作手册"，每个工具的参数、返回值、常见错误都写在这里。读完它你就知道 Agent 具体能做哪些事 |

> 💡 为什么先读 SKILL.md：它是面向"人类可读"的业务描述，比源码容易得多，却覆盖了全部业务能力。读完再看源码会有"对照答案看书"的效果。

### 阶段 1：配置与提示词（理解"Agent 是谁、被限制了什么"）

| 顺序 | 文件 | 看什么 |
|---|---|---|
| 4 | `settings.py`（237 行） | `Settings` 类的字段定义；`container_names` / `image_prefixes` / `workspaces` 三个白名单属性的解析逻辑；`model_post_init` 里 whitelist.json 覆盖 .env 的优先级 |
| 5 | `prompts.py`（101 行） | 系统提示词模板。重点看：**部署顺序约束**（第 50-63 行）、**审批闸门**、错误处理规则。这决定了 Agent 的行为边界 |
| 6 | `runtime.py`（75 行） | `RuntimeContext` 的 5 个字段（container_name / image_tag / environment / user_id / additional_info）。这是"单次部署任务"的数据载体 |

> 💡 阶段 1 结束后，你应该能回答：Agent 被允许操作哪些容器？哪些操作必须审批？部署的固定顺序是什么？

### 阶段 2：工具层（核心业务，最大的文件，分块读）

| 顺序 | 文件 | 看什么 |
|---|---|---|
| 7 | `tools/__init__.py`（2589 行） | **不要从头到尾通读**，按下面的分块顺序读 |

建议的分块阅读顺序：

1. **文件头部辅助函数**（约 1-150 行）：
   - `_ok()` / `_err()`：所有工具统一返回结构化 JSON 字符串（`{"success": true/false, ...}`），**绝不 raise 异常**——这是让 LLM 能读懂错误的关键设计
   - `_run_ssh()`：用 paramiko 在目标服务器执行命令，`asyncio.to_thread` 包装避免阻塞事件循环
   - `_build_log_queue_var`：ContextVar 实现的"实时构建日志通道"（docker build 每一行日志实时推给前端）

2. **第一个工具 `git_pull_code`**：对照 SKILL.md 的"工具 1"小节读，理解一个工具的完整套路：参数校验（白名单）→ SSH 执行 → 组装 JSON 返回

3. **`build_docker_image`**：最复杂的工具，包含流式日志输出

4. **`stop_container` / `remove_container` / `start_container`**：危险操作三件套，注意它们都在审批名单里

5. **`check_service_health`** 及其余工具（列表查询、工作区文件操作、白名单管理、回滚）

6. **文件末尾的 `build_tools(settings)`**：所有工具的汇总导出，LLM 实际拿到的就是这份清单

> 💡 每个工具的模式高度一致：`@tool` 装饰器 + async 函数 + docstring（给 LLM 看的参数说明）+ 校验 + `_run_ssh` + `_ok/_err` 返回。吃透一个，其余都能看懂。

### 阶段 3：中间件（安全防护体系）

| 顺序 | 文件 | 看什么 |
|---|---|---|
| 8 | `middleware.py`（832 行） | 按以下顺序读 5 个中间件 |

5 个中间件的职责（执行顺序 = factory.py 中注册顺序）：

| 中间件 | 一句话职责 |
|---|---|
| `AuditLogMiddleware` | 每次工具调用都写审计数据库（最外层，什么都逃不过它） |
| `RiskControlMiddleware` | 并发锁（同一容器不允许并行部署）+ 危险操作前置校验 |
| `EnvScopingMiddleware` | 参数透传（白名单校验已下沉到各工具内部） |
| `DeploymentStateMiddleware` | 工具执行后自动更新部署状态机 |
| `DeployApprovalMiddleware` | **审批中断**：名单内的工具调用触发 `interrupt()`，暂停等人工决策 |

重点精读 `DeployApprovalMiddleware`（约 115 行起）：
- 为什么 `interrupt()` 必须在 `after_model` 钩子里调，而不能在 `wrap_tool_call`（文件头注释有解释——否则中断会被 ToolNode 静默吞掉）
- reject 决策如何把错误 ToolMessage 返回并从 tool_calls 中移除（避免 OpenAI 协议报错）

### 阶段 4：持久化层（两个小数据库）

| 顺序 | 文件 | 看什么 |
|---|---|---|
| 9 | `state.py`（300 行） | `deployments` 表结构；状态机 `pending → building → deploying → healthy/unhealthy/failed/rolled_back`；`DeploymentStateStore` 的 record / get_by_thread / list_history |
| 10 | `audit.py`（207 行） | `audit_log` 表结构；风险等级（low/medium/high）与状态（ok/failed/rejected/blocked/error）的取值 |

> 💡 这两个文件与 `factory.py` 里的 `AsyncSqliteSaver`（对话检查点 checkpoints.db）是三份独立的 SQLite 数据。检查点由 LangGraph 框架管理，后两个是本项目自己写的。

### 阶段 5：组装工厂（所有零件汇合的地方）

| 顺序 | 文件 | 看什么 |
|---|---|---|
| 11 | `factory.py`（179 行） | `create_deploy_agent()`（123-179 行）是**全项目的组装点**：模型 + 工具 + 提示词 + 5 个中间件 + 检查点 + skills 挂载，全部在这里汇合。中间件的注册顺序注释（163-168 行）值得抄下来 |

### 阶段 6：API 层（最后看，最复杂）

| 顺序 | 文件 | 看什么 |
|---|---|---|
| 12 | `api.py`（794 行） | 分四段读：<br>① 文件头注释（1-21 行）：SSE 事件类型的完整清单<br>② `TOOL_STATUS_MAP` / `TOOL_HINT_MAP`（47-80 行）：工具名 → 前端展示状态的映射<br>③ `POST /api/agent/chat` 主流程：如何调用 `agent.astream()` 流式消费、如何翻译成 SSE 事件、流结束后如何用 `aget_state().interrupts` 判断是否被审批中断<br>④ 审批恢复：用户带 `decisions` 参数再次调用时如何用 `Command(resume=...)` 恢复执行 |
| 13 | `logging.py`（114 行） | 最简单，随手翻完即可 |

### 阶段 7：测试与脚本（验证理解 + 最佳示例）

| 顺序 | 文件 | 看什么 |
|---|---|---|
| 14 | `tests/test_approval.py` | 审批中断的完整断言方式，是理解审批机制的最好材料 |
| 15 | `tests/test_sse.py` | SSE 事件流的测试 |
| 16 | `tests/test_rollback.py` | 回滚流程 |
| 17 | `scripts/smoke_test.py` | 端到端冒烟测试，看一遍等于走一遍完整部署流程 |

## 四、一次完整请求的数据流（把所有模块串起来）

以用户发送"部署 my-app 仓库 main 分支"为例：

```
前端 POST /api/agent/chat {message, thread_id}
  │
  ▼
api.py：构造 HumanMessage，调 agent.astream()
  │
  ▼
LangGraph 循环（每轮）：
  LLM(ChatOpenAI) 产出 AIMessage
    │ 含 tool_calls？
    ├─ 否 → 输出文本 → message_delta SSE 事件 → 循环结束
    │
    └─ 是 → 中间件链依次处理：
        ① AuditLogMiddleware     记审计日志
        ② RiskControlMiddleware  并发锁 + 危险校验
        ③ EnvScopingMiddleware   参数透传
        ④ DeploymentStateMiddleware（执行后更新状态）
        ⑤ DeployApprovalMiddleware 检查是否在审批名单
              │
              ├─ 不在 → 执行工具（tools/__init__.py）
              │          SSH 到目标服务器跑 git/docker
              │          结果 → tool_call_end / log SSE 事件
              │          回到 LLM 进入下一轮
              │
              └─ 在名单 → interrupt() 中断！
                         → approval_required SSE 事件
                         → 前端弹审批框
                         → 流结束（awaiting_approval 状态）

用户点击"同意" → 前端再次 POST /api/agent/chat {decisions: [{approve: true}]}
  │
  ▼
api.py：Command(resume=decisions) 恢复被中断的图
  → 从断点继续执行工具 → 后续流程同上
```

## 五、给初学者的阅读技巧

1. **善用 docstring**：本项目每个文件头、每个类、每个函数都有中文 docstring，且解释的是"为什么这样设计"（比如为什么用 ContextVar 传日志队列、为什么列名要转义）。**先读注释再读代码，效率翻倍。**

2. **对照测试读源码**：看到不懂的函数，去 `tests/` 里搜它的名字，测试代码会展示典型输入输出。

3. **跑起来看日志**：`logs/deploy_agent.log`（loguru 落盘）里每次工具调用都有 `tool=xxx | args=xxx | ok | elapsed=xxxms` 格式的记录，对照源码看日志能快速建立直觉。

4. **用 scripts 查数据**：`python scripts/inspect_db.py` 可以直接看三个 SQLite 库里存了什么，把抽象的"检查点/部署状态/审计"变成具体数据。

5. **先横后纵**：第一遍按本指南顺序"横向"过一遍建立地图；第二遍选一条主线"纵向"深挖（推荐主线：审批流程，从 `middleware.py` 的 interrupt 到 `api.py` 的 decisions 恢复）。

## 六、名词解释（按首次出现顺序）

| 名词 | 解释 |
|---|---|
| **Agent** | 能自主决策"调用哪个工具、传什么参数"的 LLM 程序。LLM 是大脑，工具是手脚。 |
| **Tool（工具）** | Agent 能调用的函数。用 `@tool` 装饰器声明，docstring 会发给 LLM，LLM 根据它决定怎么传参。 |
| **System Prompt（系统提示词）** | 开场就发给 LLM 的"岗位说明书"，规定角色、规则、约束。见 prompts.py。 |
| **SSE** | Server-Sent Events，服务器向浏览器单向推送事件的 HTTP 长连接技术。前端看到的"正在拉取代码…"等实时进度就是它。 |
| **Middleware（中间件）** | 包在工具执行外层的拦截器，可在工具执行前后插入自定义逻辑（审计、审批、风控）。 |
| **interrupt（中断）** | LangGraph 的机制：暂停整个执行图并保存现场，等外部输入（这里是人工审批决策）后再恢复。 |
| **thread_id** | 一次对话会话的唯一标识。LangGraph 用它区分不同用户的会话记忆。 |
| **Checkpointer（检查点）** | LangGraph 的会话持久化组件。每一步执行后的状态都存进 SQLite（checkpoints.db），进程重启后会话还能续上。 |
| **ContextVar** | Python 的"协程局部变量"，同一个 HTTP 请求内的代码能共享数据，不同请求之间隔离。用于传递实时构建日志队列。 |
| **白名单** | 允许操作的容器名/镜像前缀/目录列表。不在名单内的操作直接拒绝，防止 Agent 误伤其他服务。 |
| **状态机** | 部署状态只能沿合法路径流转（pending → building → deploying → healthy），不能跳跃。 |
| **冒烟测试** | 快速验证主流程能否跑通的最小测试。 |

## 七、阅读完成的自查清单

读完本指南路线后，试着回答这些问题检验理解程度：

- [ ] Agent 一共能调用哪些工具？哪些必须人工审批？
- [ ] 一条用户消息从 HTTP 进入到 SSE 事件输出，经过了哪些模块？
- [ ] `interrupt()` 为什么必须在 `after_model` 钩子中调用？
- [ ] 工具执行失败时为什么不抛异常，而是返回 `{"success": false}` 的 JSON？
- [ ] 三个 SQLite 数据库（checkpoints.db / deployments.db / audit.db）分别存什么？
- [ ] 白名单有几种？各自的来源和优先级是什么（.env vs whitelist.json）？
- [ ] docker build 的日志是怎么实时推到前端的（ContextVar + Queue 的协作）？
- [ ] 部署失败后回滚（rollback）是怎么实现的？

全部能答上来，说明你已经掌握了这个后端的完整脉络。
